# 统计口径说明与核对记录

日期：2026-10-26　数据：`~/.dsh/sessions` 全量解压后的 1,009 个日志，折叠出 157,527 步（每步 >300ms）

这份文件回答两个问题：**之前的数字是怎么算的、错了没有**；以及**现在界面上出现的每个数字，定义是什么**。

## 一、「超过 p75 的异常步只有 7.6%」这个数不成立

旧数是 `E:/DSH/patch/eval/stepstat.mjs:122` 算出来的，它做的是：

1. 把每一步切成 25% / 50% / 75% 三个时间点（检查点）；
2. 在每个检查点，取**过去同类步的 p75**（要样本 ≥3）；
3. 数「这个检查点的**已用时间** > p75」的比例，分母是"有历史样本的检查点数"。

问题有三处，任何一处都足以让这个数不可用：

- **比错了对象**：拿「这一步已经跑了多久」去比「同类步**跑完**的 p75」。跑到 75% 刻度时已用时间天然小于整步 p75，比例被系统性压低。
- **基线混入自己**：代码先把当前步的耗时 push 进历史，再算分位（`stepstat.mjs:111` 在 109 之后），基线包含了被评估者本身，称为 in-sample。正确做法是留一法或只用前序样本。
- **分母是检查点不是步**：一条 20 秒的步贡献 3 个检查点，一条 0.4 秒的步贡献 0 个，长步被过度加权。

**同一批数据、换成正确的口径重算**（`E:/DSH/patch/eval/step-audit.mjs`，155,727 个不进上下文维护的步）：

| 口径 | 定义 | 「超过 p75」的比例 |
|---|---|---|
| 全量合并 p75 | 所有步的 p75 作一条基准 | **25.0%**（按 p75 的定义必然如此） |
| 留一法（out-of-sample） | 每个工具调用与「同类别同工具名的其余全部样本」的 p75 比 | **24.5%**（n=65,458） |
| 同会话前序样本（界面运行时能看到的） | 每个步与「本会话此前同类步」的 p75 比，样本 ≥5 才算 | **27.9%**（n=141,784） |

结论：**p75 的本质就是"25% 的样本比它慢"，7.6% 是口径错的产物，不能用于任何判断**。正确说法只能是"约四分之一的操作会比同类常见上限更慢"，这也说明「超过 p75」本身**不能当作异常信号**——它就是常态。所以界面只在**显著超出**时提示，并且措辞是"耗时异常"，不是"停滞"。

## 二、步耗时的拆分口径（0.1.6 起）

一步的总时长会被拆成互不混算的三段，界面上分列，基线与样本也分开存：

| 段 | 定义（事件口径） | 归入类别 |
|---|---|---|
| 模型 | `step/start` → 该步第一个 `tool/call`；若一步没有工具，则 `step/start` → 下一步开始 | `model|签名` |
| 本地工具 | `tool/call` → 对应 `tool/result`，工具属读写/命令/编辑等 | `tool|local|签名` |
| 网络工具 | 同上，工具属 `web_search`/`web_fetch`/browser 等 | `tool|network|签名` |
| 后台等待 | 子代理、定时、`job_output` 等；`ask_user_question` 包含在内 | 不进任何基线 |
| 上下文维护 | `compress`/`decompress`/`search_context`/`acp_status` | 不进任何基线，也不计任务步数 |

全量数据下的实际分布（同一次审计）：

- 步总时长：中位 4.6s，p25 3.2s，p75 7.5s，p90 14.9s；
- 其中**模型段**：中位 4.3s，p75 6.7s——可见"步耗时"绝大部分是模型推理，把工具混进去会掩盖真实差异；
- **工具调用**：中位 413ms，p75 794ms，p90 4.2s；按类型看差异极大：`read` 中位 10ms、`write` 24ms、`edit` 26ms、`pwsh` 583ms、`bash` 3.9s、`web_fetch` 801ms、`web_search` 5.3s、`ask_user_question` 51.7s（等待人，已排除）；
- 有上下文维护的步 1,800 个，全部排除在基线之外。

## 三、界面上的数字分别是什么

| 界面文字 | 定义 | 不足时 |
|---|---|---|
| `确定 2/4 · 50%（按当前清单）` | todo 已完成/总数，真实比例 | 没有 todo 就不显示，不猜 |
| `本步 5.2s · 模型 4.1s · 工具 1.1s` | 当前这一步的事实拆分 | 照常显示，只是不比较 |
| `模型耗时异常` / `本地工具耗时异常` / `网络工具耗时异常` | 该段超过**同类别同签名**前序样本 p75，且样本 ≥5 | 样本不足只写 `参照样本不足` |
| `未知 · 已 3m20s` | 只有真实已耗时 | — |

所有比较都用**前序样本**（不会把当前步算进基线），样本门槛 5；不使用时长、token、回合数评价任务是否有进展。

## 四、与决策回合模块的边界

- 耗时统计只写 `stepStats`（`model|…`、`tool|类别|…`）与 `step*` 字段；
- 决策模块只写 `decisions` / `decisionCounts` / `stall`，读取同一批事件但不读耗时字段；
- 两套判断互不引用：**耗时异常不会触发"疑似停滞"，"疑似停滞"也不改任何耗时样本**。将来接更细的有效进展分析，直接消费 `decisions` 即可，不需要动耗时基线。
