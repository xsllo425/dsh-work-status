# 社区进度类插件的做法调研

日期：2026-10-26　范围：9 个 DSH 进度/状态类社区插件（逐个读过 README 与协议文档）
用途：为 `dsh-work-status` 的「进度」部分选路线。不复制代码，只吸收思路；引用代码需各自遵守许可证（见文末）。

## 一句话结论

九个项目里，**没有一个能靠事件流算出可靠的整轮 ETA**；能立住的只有三类东西：

1. **真实确定量**：todo 清单的完成比例（uuhihj、omdsh-dev 都这么做，且都注明"只是当前清单"）；
2. **同类样本参照**：本机历史同类耗时（2008924 按 cwd 会话中位数、uuhihj 按"第几步"查分位表）；
3. **状态语义**：卡住/超时/等待人/后台在跑/结果未知（Rice00 心跳、dsh-task-progress 的 ended 推断、LUgABeEEE 的完成确认）。

这也和我们自己的全量评测一致：整轮 ETA 在 2 分钟以内勉强可用，5 分钟以上基本等于乱猜；把"步"当最小统计单元反而稳（中位数 4.6s，p25–p75 3.2–7.6s，超 p75 的异常步只有 7.6%）。

## 逐个看

### uuhihj/task-progress-bar（鲸程，MIT，v0.4.0）
- 做法：事件流驱动阶段；**ETA 分三档**：todo 存在时用「已完成项平均耗时 × 剩余项数」；否则按"已跑到第几步"查真实分位分布（统计自 1481 个真实任务）；本机攒 20 条样本后替掉内置表。
- 态度：作者明说旧算法"平均估高 2–6 倍"，所以改成查分布；超过常见耗时只报橙色「已超预估」，**不再继续倒计时**。
- 可借鉴：todo 优先 + 分位表 + 本机自校准 + 显式超时态；子代理单独一行、默认折叠。
- 注意：它的"阶段模板"是按任务类型猜的（修 bug=定位→实施→验证），会标注"自动估计"——**猜的阶段不能当真实进度**。

### omdsh-dev/dsh-ui-progress（BSD-3-Clause，v0.11.x）
- 做法：纯客户端插件挂输入框停靠区；填充宽度 = todos 真实比例（(完成+进行中)/总数），**没有 todos 就固定 100%**，不画伪百分比。
- ETA：v0.8 起只认模型上报的 `eta` 字段，不线性外推；模型不报就不显示。宿主半区为空，零提示词注入。
- 状态：等待审批/选择（琥珀）> 运行中（蓝）> 中断（橘红）> 完成（绿）> 空闲。中断以 `turn/end reason` 为主信号。
- 可借鉴：**无数据不画百分比**这条纪律；状态优先级；token 速率用"已结算 step 的真实 usage"自校准。
- 注意：它的 100% 是"不知道就不显示进度"的表达，被我们第一轮的"完成 N 步"取代，但纪律一致。

### 2008924/dsh-progress-viz（MIT，Python 看板）
- 做法：直接读 `~/.dsh/sessions/**/session.jsonl.zstd`；阶段 = todo 第一个未完成项，无 todo 用 `step/start` 计数兜底。
- ETA = `α·linear + (1−α)·hist`：linear 是"已走阶段平均耗时 × 剩余阶段"；hist 是同 cwd 历史会话耗时**中位数**；α 随阶段数自适应（k≥3→0.7，k==2→0.5，k<2→0）。`eta_mode` 明确标 `blend/linear/history/none`。
- 坑（值得记）：zstd 必须 `stream_reader` 流式解压，`decompressobj` 只解第一帧（我们踩过同款）。
- 可借鉴：**来源标签**（告诉用户这个数是按什么推的）；中位数而非均值；无历史就 `none` 不硬编。

### chen8923/dsh-task-progress（MIT，v0.3.0）
- 做法：生产者（脚本）往追加-only JSONL 写 `{state,pct,done,total,msg}`；宿主只读尾部 256KiB，前端 2s 轮询。
- 关键设计：**结局不只有生产者能写**——进程被杀时 `finally` 不执行（Windows taskkill 不跑用户代码，实测过），所以由 job registry 补一个 `ended:{job,status}` 推断结局，并明确"推断 vs 上报"。
- 坑：`ctx.jobs.read()` 会**偷走模型要读的输出和完成通知**（单消费者游标），绝不能碰；只读 registry 快照。
- 可借鉴：`ended` 这类"这是推断"的显式标记；心跳/沉默语义（60s 无更新标"无更新"）；一条任务一个生产者。

### Rice00/dsh-job-progress（MIT，v1.0.x）
- 做法：后台 job 场景；生产者写 JSON（done/total/unit/speed/eta/phase/status），**total:0 显示"running, unknown size"**；运行中要求 ≤15s 心跳，停写即视为消失；完成后保留 2 分钟。
- 可借鉴：未知总量就明说未知；心跳缺失 = 不可区分于崩溃；原子写（tmp + rename）。
- 注意：它不算"任务进度"，只算"job 进度"，两者别混。

### Yu-jianhai/dsh-session-progress（MIT，v0.x）
- 做法：每 30s 用**最便宜的模型**读当前轮上下文，返回 0–100，画在会话行底色带上；封顶 95，`turn/end` 补满；允许模型看见上次估值以自我下调；被中断的轮次记下百分比，下次接续。
- 代价：每会话每 30s 一次真实调用，约 1–2k 输入 token。
- 可借鉴：**方向允许下跌**（返工时进度可以退）、"上一轮到 X%"作为接续背景。
- 不学：周期性真实模型调用——我们的要求是零额外调用。

### LUgABeEEE/dsh-global-todo（MIT，v0.13）
- 做法：跨会话 todo；**Agent 说完成只进"待确认"**，人确认才算完成；`error/aborted/interrupted/max-tokens` 一律不标记完成。
- 可借鉴：完成语义只在 `by === 'agent'` 一处实现；"失败的一轮挂着完成标签是让整份清单不可信的起点"。
- 注意：它管的是待办清单，不是进度百分比。

### yiliang114/dsh-session-deck（MIT，v0.1.x）
- 做法：只做**状态**不做进度：running / waiting / unread；父会话在有子代理运行时保持 running；状态词只写能证实的档位（"已结束"而不是"成功"）。
- 可借鉴：状态优先级（等待 > 运行 > 未读）；子代理继承运行态；措辞克制、不宣称成功。
- 注意：它依赖 rc.2 的 DOM 结构做落位，宿主升级易碎——我们只用插槽。

### PerryLink/dsh-fast（Apache-2.0，v0.1.x）
- 做法：只读性能诊断：会话加载耗时、spill 命中、压缩次数与 shadowed tokens、上下文注入体积、缓存命中率；每事件 O(1) 折叠、定时快照，**绝不进模型热路径**。
- 可借鉴：测量/呈现全部移出模型路径；折算是 O(1) 的、快照是定时异步的；降级要"说一次"而不是静默改数字。

## 横向对比

| 维度 | 做得最好的 | 共同问题 |
|---|---|---|
| 进度确定性 | omdsh-dev（有 todo 才画比例） | 没有 todo 时几乎所有实现都在猜 |
| ETA | uuhihj（分位 + 自校准 + 超时态） | 长轮仍然不准；多数不标"这是估计" |
| 真实事实 | dsh-fast / Rice00 | 只覆盖后台 job 或性能，不覆盖对话 |
| 失败与未知 | dsh-task-progress / LUgABeEEE | 推断结局容易与真失败混淆 |
| 性能 | dsh-fast（O(1) 折叠 + 定时快照） | 轮询式实现（4s/2s）在大日志上会重扫 |

## 对我们的建议（结合已有评测）

1. **整轮 ETA 不做**。全量 14,418 轮评测：5 分钟以上误差 210–3029s，不如"历史中位数"基线；给了 ETA 的检查点占 88%，等于过度承诺。
2. **保留 todo 的真实比例**（确定模式），并且明确标注"只是当前清单的比例"。
3. **以"步"为最小参照**（已实现 0.1.3）：当前这一步耗时 vs 同会话同类步的 p25–p75；超过 p75 说"比 75% 的同类步更久"，不预测整轮。
4. **超时改成事实**：不写"还要 X"，写"已超过历史 75% 时长（同类步通常 3–8 秒）"。
5. **状态语义按社区共识**：等待人（审批/选择）优先于运行；子代理在跑则父会话保持运行；失败用"没跑成/没压成"这类无副作用措辞，推断出来的结局必须标"推断"。
6. **性能纪律**：折叠 O(1)、快照定时、渲染节流；不调模型、不注提示词、不碰 `ctx.jobs.read()`。
